# Planted-bug benchmark: NER, gpt-4

Generated by `benchmark.py`. 10 single-component breaks injected into the real gpt-4 NER
prompt (`upstream/ner_fewshot.cfg`), each re-run for real against gpt-4 (3 runs × 20 inputs =
60 calls) and compared against the stored, untouched gpt-4 baseline
(`results/ner__gpt-4__gpt-4.jsonl`). Real spend this run: **$14.18**.

## What each column means

- **Caught**: did the break produce at least one `REGRESSED` verdict against the baseline?
- **Component named**: among the regressed inputs' cause suspects, did the actual broken
  component appear anywhere (not necessarily ranked first)?
- **Component top-ranked**: was it suspect #1?
- **Fix accepted**: did a *single* fixer attempt (gpt-4 proposing one edit, no retry) bring
  regressions to 0? `migrate.py` itself retries up to 3 times with feedback from rejected
  attempts; this benchmark used 1 attempt per break to keep cost predictable, so this is a
  lower bound on what the full tool would do.

## Reading these numbers honestly

- **Catch rate is low (0.4) because gpt-4 is robust and the input set is small (20 inputs).**
  Six of the ten breaks (both "blur" breaks that just dropped examples, and the INGREDIENT
  contradiction) didn't change gpt-4's output on any of the 20 inputs at all — the model
  already knew what a dish/ingredient/equipment is from the label name and few-shot examples,
  so trimming or softening the definition text didn't move it. The breaks that *were* caught
  all hit a specific tricky input already in the set (`ner-03`, `ner-15`/`ner-20`, `ner-16`) —
  catch rate measures the input set's coverage of a given prompt component as much as it
  measures the tool's sensitivity. More inputs, especially ones deliberately designed to probe
  each label definition, would likely raise this.
- **Right-component rate is perfect (1.00) when something is caught**, but **top-ranked rate is
  only 0.50** — the cause-finder's suspect list is a true superset (it never missed the real
  culprit outright) but its ranking heuristic sometimes puts a different editable component
  first. In break02 and break03, the real bug was in `description`, but `label_definitions.EQUIPMENT`
  ranked higher, and the fixer edited that instead — a wrong-but-plausible pick, since both
  attempts correctly caught the regression but fixed the wrong thing.
- **Fix rate (0.25) reflects one fixer attempt, not three.** The one break that *did* get
  fixed in one shot (break06) is also the one where the top-ranked suspect was correct. The
  two `description` breaks failed their one-shot fix for the same reason they weren't
  top-ranked: the fixer edited `EQUIPMENT` rather than `description`. `migrate.py`'s real loop
  would feed that rejection back and could try `description` next; this benchmark doesn't
  test that retry path.
- **Zero false alarms** on a completely fresh, unpatched gpt-4 re-run (3 new runs, 20 inputs,
  real API calls) confirms the regression rule doesn't fire on ordinary model noise alone —
  the method's specificity looks solid even though this run's sensitivity, on this small input
  set, is partial.

## Cost

Actual spend, from real `cost_usd` fields in the recorded rows: **$14.18** for all 10 breaks
(4 of which also triggered a fix-verification re-run) plus the false-alarm re-run. In line
with the ~$10–15 (up to ~$19 worst case) estimate given before running.

## Line-level ablation on the 4 caught breaks (Oct 7)

`python benchmark.py --ablate` reuses each break's cached run, then for every regressed input removes one
sentence (or "e.g." example list) at a time and re-runs gpt-4 3x. A unit is *confirmed* when removing it makes
the input stop regressing. A control re-run of the unablated broken prompt stayed REGRESSED for all 5 inputs,
so these regressions are stable, not noise. Cost $1.91 (about 135 gpt-4 calls). Details: `ablation.json`.

| Break | Planted change | Heuristic top = right component | Ablation top = right component | Planted unit confirmed | Other units confirmed |
|---|---|---|---|---|---|
| break02 | deleted "Adjectives, verbs, adverbs are not entities." | no | no (nothing confirmed) | n/a (deletion) | none |
| break03 | adjective rule replaced by a contradiction | no | no | **no** | `INGREDIENT#0` |
| break06 | DISH examples + "including raw ingredients…, e.g. sliced tomatoes" | yes | no | **no** | `description#1`, `description#2`, `EQUIPMENT#0`, `INGREDIENT#0` |
| break10 | EQUIPMENT examples + "bowl, plate, cup" | yes | **yes** | **yes**, the only one | none |

**Top-ranked rate: 2/4 (heuristic) → 1/4 (ablation).** Single-sentence removal is worse than the heuristic here.
Why, from the data:
- **Missing instructions can't be found by removal** (break02, and the real gpt-5.6-sol regression on ner-16,
  where the accepted fix *adds* a clarification).
- **A misread line that is also needed** (break03): removing it leaves the instruction missing, so the input
  stays broken.
- **A plant spanning two units** (break06): removing either half leaves the other half in place.
- **Low specificity:** removing unrelated sentences flipped 2 inputs. "Removal repairs it" means the input is
  sensitive to that sentence, not necessarily that the sentence is the cause.

Where it works: a single added line that the model over-applies (break10 here, and the planted agent line in
`reports/agent/linefinder_gpt-5.6-sol.json`, where only the planted line out of 8 repaired 3/3).
